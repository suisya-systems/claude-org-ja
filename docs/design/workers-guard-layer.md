## 0. 層の選択と独立に、先に手当てが要る発見

### 0.1 動いているガードのバージョンを誰も検査していない

本調査の最中、**実際に発火していたフックは修正適用前の版だった**。

- フックは各 role の `.claude/settings.local.json` に **絶対パスで**配線されている。したがって「動いているガード」は常に **ja ルートのワーキングツリーの現在の中身**であって、マージ済みの内容ではない。
- ja ルートの checkout が旧コミットに留まっていた期間が実測で **約 17 時間**あり（`git reflog` による）、その間 `renga x; rm -rf ../workers/foo` は**素通り**していた（旧版で PASS / 修正版で BLOCK）。
- 窓口・ディスパッチャー・リポジトリ内 worktree は同じ絶対パスを参照するため、**揃って**旧版を継承していた。
- 現在は解消済み（ワーキングツリーが最新に追随し、配備されているのは修正版 256 行）。

これは既知の劣化モード（cwd 依存 / 相対パス配線）とは別の**第 3 のモード = 「マージしたが pull していない」**である。実害は観測されていないが、性質が悪いのは次の点である:

> **ガードが無効化されていることを、誰も・何も検出しない。** フックは黙って `exit 0` を返すだけなので、無効化は成功と区別がつかない。

**どの層を採用するかと無関係に、「配備されているガードの版が期待どおりか」を検査する仕組みが要る。** 本書の推奨（[§6](#6-推奨と段階移行)）に必ず含める。

### 0.2 フックでは原理的に見えない削除経路が、コードとして実在する

[`tools/state_db/curator_archive.py`](../../tools/state_db/curator_archive.py) の `--purge` は、`worker_dirs` テーブルの `lifecycle='delete_pending'` 行を選び、**`workers_root` 配下かどうかを検査せずに `shutil.rmtree()`** する。その `delete_pending` は人間の明示判断ではなく、ヒューリスティック分類器が付ける（インベントリの `archive_candidate` を機械的に写像している）。`apply_archive()` 側の `--workers-root` 既定値は `Path("..")` であり、ja ルートから見ると `../workers` ではなく**その 1 つ上**を指す。

現状は**潜在**である（実測: 呼び出し元ゼロ・スケジューラ登録ゼロ・`worker_dirs` 63 行はすべて `active` で `delete_pending` は過去に 1 件も無い）。

しかしこれは、本調査の中心的な主張の具体例として重要である:

> `python -m tools.state_db.curator_archive --purge` というコマンド文字列は、**現行フックを PASS する**（実測）。文字列には `rm` も `workers` も現れないが、実行されれば再帰削除が起きる。**プログラムが行う削除は、コマンド文字列の解析では原理的に見えない。**

本件の修正は本調査の範囲外だが、独立課題として起票する価値がある。

## 1. 背景と問い

ワーカー作業ディレクトリの削除抑止は [`.hooks/block-workers-delete.sh`](../../.hooks/block-workers-delete.sh) が担っており、方式は「Bash コマンド文字列を解析して破壊的操作かどうかを当てる」である。シェルコマンド文字列から実際に何が削除されるかは原理的に決定できないため、この方式は fail-open の穴を構造的に持ち続ける。穴を 1 つずつ塞ぐアプローチには終わりがない。

本書はこれを踏まえ、**どの層で担保すべきか**を実測に基づいて評価する。

### 1.1 この組織には既に「同型問題の結論」がある

ローカルの curated ノート `knowledge/curated/permissions-sandbox.md`（git 追跡外）は、別件（spawn argv の制約）で得られた結論をこう記録している:

> 「危険入力を列挙して弾く」後追いは収束しない。**default-deny の allowlist** にすると一発で閉じる。
> 同一カテゴリで 3 round 消えない指摘は、パッチを積まず方式転換のサインとみなす。

現行フックは**まさにこの blacklist 型**である。本書はこの既存結論を、削除抑止の文脈へ適用し直すものでもある。

### 1.2 現行フックの改修履歴が示すもの

直近の改修（renga 例外の構造化）は 4 コミットを要したが、その内訳が方式の性質を示している:

| コミット | 内容 | 種別 |
|---|---|---|
| 1 | renga 例外を構造判定へ（回避 4 件を塞ぐ） | 穴を塞ぐ |
| 2 | 例外の内側のコマンド置換経由の削除を塞ぐ | 穴を塞ぐ |
| 3 | リダイレクトの `&` を区切り扱いして**正当な起動をブロックしていた** | **偽陽性の修正** |
| 4 | ダブルクォート内のエスケープ済み引用符で分割し**正当な起動をブロックしていた** | **偽陽性の修正** |

**4 round のうち 2 round が「締めたことで生まれた偽陽性」の修正**である。文字列解析を締める方向は、抜けと偽陽性を**同時に**増やす。これは推測ではなく、この組織自身の改修履歴に現れた事実である。

## 2. 実測で確定した現状

### 2.1 いま `../workers` を守っているのはフックではない

**実測**: エージェントのセッションから `../workers` は**読める**が**書けない**。そして `../workers` に対応するマウントは**名前空間に 1 つも存在しない**。

```
ls ../workers/                        -> OK（読める）
grep -c "org/workers" /proc/self/mountinfo -> 0（マウントが無い）
touch ../workers/...                  -> Read-only file system
```

これは Claude Code の sandbox が「**全体を読み取り専用で bind し、書ける場所にだけ穴を開ける**」方式であることによる。すなわち:

> **`sandbox.filesystem.additionalDirectories` は read の許可ではなく write の許可である。** read は grant 無しで通る。

したがって現在 `../workers` を守っているのは、フックではなく **「書き込み用マウントが存在しないこと」**である。この防御は:

- **カーネルが強制する**（プロセスがどう書こうと EROFS）
- **意図を一切見ない**。したがって `rm` / `find -delete` / `shutil.rmtree` / `rsync --delete` / `mv` / `git worktree remove` を**区別せず同じように**止める

一方でこの防御は**意図されたものではなく、設定が宣言と食い違っている結果**である（[§4.4](#44-schema-と実配布のずれ問い-c)）。

### 2.2 sandbox の実装形

**実測**: Claude Code の Linux sandbox は bubblewrap 方式のマウント名前空間であり、「許可ディレクトリ内の一部を禁止する」は **rw マウントの内側に ro マウントを入れ子にする**ことで実装されている。自セッションの `/proc/self/mountinfo` より:

| mount | パス | 属性 |
|---|---|---|
| 875 | ワークツリー本体 | `rw` |
| 876 / 877 | `.claude/settings.json` / `settings.local.json` | `ro`（875 の入れ子） |
| 890 | ワークツリーの `.git` | `ro` |

補足的な実測事実:

- **マウント点が存在しない場合、sandbox はそれを作る**。`.bashrc` / `.gitconfig` / `.idea` 等が 0 バイト `-r--r--r--` として実体化され、その上に `/dev/null` を bind している。セッション開始直後の `git status` にこれらが未追跡ファイルとして現れるのは、この副作用である（従来「原因不明の未追跡ファイル」として見えていたものの説明になる）。
- **マウント集合はセッション内の Bash 呼び出しをまたいで同一**（実測: 別々の Bash 呼び出しで `readlink /proc/self/ns/mnt` が同一 ID を返す）。すなわち deny 集合は**起動時のスナップショット**であり、起動後に作られたパスは遡って保護されない。

### 2.3 現行フック（L4）の実測性能

コーパス: エージェントの実トランスクリプトから抽出した **11,705 件**の Bash コマンド。配備中の修正版フックを実際に走らせた結果:

| 指標 | 実測値 |
|---|---|
| ブロック総数 | 17 |
| うち本当に workers 配下の再帰削除だったもの | **1** |
| 適合率 | **5.9%** |
| 手作りの回避パターン 24 件のうち通過した数 | **20** |

通過した回避の代表例（いずれも実際に破壊的）:

```
find ../workers/foo -mindepth 1 -delete
python3 -c "import shutil; shutil.rmtree('../workers/foo')"
mv ../workers/foo /tmp/gone
rsync -a --delete /tmp/empty/ ../workers/foo/
git worktree remove --force ../workers/slug/.worktrees/task
/bin/rm -rf ../workers            # 先頭境界の正規表現に一致しない
rm -rf /home/happy_ryo/work/org   # 親を消す。workers の文字列が現れない
x=$(cd .. && pwd)/workers/foo; rm -rf "$x"   # 変数経由（フック自身がコメントで限界と明記）
```

一方でブロックされた 17 件の大半は**無害**であり、その中には **このガードを修正・起票する作業そのもの**が含まれていた（`rm -rf ../workers` という文字列を本文に含む issue 起票コマンド等）。調査中には、単に当該フレーズを引用しただけの `echo` がブロックされる事象も再現した。

構造的な限界は 3 つあり、いずれも実装の抜けではなく**方式の性質**である:

1. workers パスを **4 通りの綴りの固定文字列照合**でしか見ない
2. `rm` の検出正規表現が**先頭境界を要求**するため `/bin/rm` が不可視
3. **祖先ディレクトリの削除**は workers に言及しないので検知対象にすらならない

## 3. 脅威モデル

### 3.1 実測に基づく順位

| | 脅威 | この組織での実測 evidence |
|---|---|---|
| (a) | エージェントのうっかり事故 | **唯一、実頻度が測れる**。`../workers` 配下では close ごとに `git worktree remove` が正当に走る（実測: `worker_dir` が紐付く完了 Pattern B run 33 件中 26 件が `../workers` 配下。全体では下限値）。過去にはフックが窓口を止め、人間が手で削除を実行して解決した記録もある |
| (c) | スクリプトのバグ | 実コードが存在（[§0.2](#02-フックでは原理的に見えない削除経路がコードとして実在する)）。ただし呼び出し元ゼロ・スケジューラ登録ゼロ・該当行ゼロで**潜在** |
| (b) | 外部注入 | リポジトリは public。issue 本文と全コメントを連結して Bash 可能 role に渡す経路が存在する。フックの回避は容易（24 件中 20 件通過） |

**同一ユーザー権限の外部攻撃者は対象外とする。** `../workers` は 755 でエージェントと同一 uid 所有であり、守るべき権限境界がそもそも存在しない。これが可能な状況なら、ガード以前に前提が崩れている。

### 3.2 重要な性質: 層の選択は脅威モデルにほとんど依存しない

これは調査で得られた、やや意外な結論である。

> **カーネル層（L3）は意図を一切見ないため、(a)(b)(c) を区別せず同じように止める。**

したがって「どの脅威を想定するか」で主たる層は変わらない。脅威モデルの選択が実際に効くのは、**(c) を想定するなら、削除を実行するプログラム自身にも containment 表明を入れるか**という 1 点だけである。

この構造のため、本書の推奨は脅威モデルの確定を待たずに骨格が決まる。確定は「(c) 向けの追加作業を含めるか」の判断に相当する。

### 3.3 確定した脅威モデル

**人間の判断により、(a) うっかり事故 + (c) スクリプトのバグ を想定脅威とする。**

- 主たる層は **L3（カーネル層）**。
- (c) を想定に含めるため、**削除を実行するプログラム側に containment 表明を入れる**ことを推奨に含める（[§6.2](#62-3-つの具体的な動き) の 2）。
- **(b) 外部注入は明示的な設計目標に含めない。** 防御機構が増えず監査コストだけが増えるためである。ただし [§3.2](#32-重要な性質-層の選択は脅威モデルにほとんど依存しない) のとおり **L3 は意図を見ないので、結果として (b) も同じように止まる**。これは設計目標ではなく副次的性質であり、(b) への防御を主張する根拠には使わない。
- **同一ユーザー権限の外部攻撃者は対象外**とする。

## 4. 層ごとの成立性

### 4.1 ファイルシステム層（問い D）

**結論: ガードとしては不成立。** 個別 inode に対する保護は**husk 問題**で無力化される。

**実測**: 保護は「フラグを立てたディレクトリの直下エントリ」までしか及ばない。`chmod 555` を掛けたディレクトリに対して `rm -rf` を撃つと、直下のファイルは残るが**その下は全部消え、空のディレクトリの殻だけが残る**。中身を守るには再帰的な凍結が必要で、それは同一所有者の `chmod -R u+w` 一発で解除できる（実測 exit 0）。

各手段の評価:

| 手段 | 脅威を止めるか | 派遣を壊すか | 運用者の手作業 | 判定 |
|---|---|---|---|---|
| `chattr +i`（個別ワーカーディレクトリ） | 再帰凍結なら止まる | 再帰凍結はワーカーの書き込みを全部壊す | **エージェントは設定不可**（EPERM。ネストした userns の root でも capability が空）。host の sudo は対話パスワードを要求 | 不可 |
| `chmod` / sticky bit | 実質ゼロ（所有者は自分） | `chmod 555 ../workers` で `mkdir` が失敗 = **派遣が死ぬ** | — | 不可 |
| POSIX ACL | 所有者を恒久的に拒否できない | — | `acl` パッケージ未導入 | 不可 |
| 所有者分離（別 uid） | 止まる | — | 単一ユーザー WSL2 で全認証情報が `/home/happy_ryo` 配下。実運用が成立しない | 不可 |
| スナップショット FS | 予防ではない | — | `/` は ext4。btrfs/zfs/LVM 無し、`cp --reflink` 非対応 | 不可 |

**ただし「読み取り専用マウント」だけは正しい意味論を持つ。** そしてそれは実質的に FS 層ではなく **sandbox 層**であり、そこでは root を必要としない（[§4.2](#42-sandbox-層問い-b)）。

**復旧手段としては採用価値がある**（[§5](#5-選択肢の比較) の O6）。ハードリンクスナップショットは実測で復元可能だったが、**同じエージェントがスナップショットも削除できた**（exit 0）ため、予防ではなく backstop としてのみ数える。

### 4.2 sandbox 層（問い B）

**結論: 「書き込みは許可・削除は不可」は、保護の単位をディレクトリのライフサイクルに合わせれば表現できる。ただし現在の設定面からは記述できない。**

#### 4.2.1 カーネルが区別できないこと / できること

まず土台となる事実を正確に述べる。

> **カーネルは「ファイルを作る」と「ファイルを消す」を区別できない。** どちらも同じ親ディレクトリへの write 権限で決まる。

したがって **1 つのディレクトリについて「書けるが中身を消せない」は、どの粒度でも表現できない**。マウント形ごとの実測は次のとおり:

| マウント形 | そのディレクトリへの書き込み | `rm -rf` の結果 |
|---|---|---|
| rw 親の内側に **ro 子** | **不可**（子は完全に読み取り専用） | サブツリーは**完全に残る** |
| **ro 親**の内側に rw 子 | 可 | **中身は全部消える**。ディレクトリの殻だけ残る |
| rw 子の内側にさらに **ro `.git`** | 可 | 作業ファイルは消えるが**コミット済み履歴は残る** |

#### 4.2.2 保護の単位をライフサイクルに合わせると成立する

上表は「同じディレクトリで両立しない」ことを示すだけで、「表現できない」ことは意味しない。**完了したタスクのディレクトリは、もう書き込む必要がない**からである。

**実測**: `../workers` 全体を rw で bind しつつ、**既存の `<slug>/.worktrees/<task>` 1 つ 1 つに ro を入れ子にする**形（以下 V3）は、次のすべてを同時に満たした:

- `mkdir <workers>/newproj` → OK（新規プロジェクトの受け入れ）
- `git worktree add` → OK（**再委譲が壊れない**）
- ブリーフ書き込み・プロジェクトルートへの書き込み → OK
- `rm -rf <task>` → 失敗（7 件のエラー）、成果物は残存
- `rm -rf <project>` → タスクのサブツリーは**丸ごと残存**

つまり「**完了した仕事は凍結し、動いている仕事は書ける**」というポリシーは、カーネル層で表現可能である。

#### 4.2.3 それでも現在は採用できない理由

**実測**: `denyWrite` の**グロブは Linux 版 Claude Code 2.1.220 で展開されない**。deny 集合はリテラルに列挙する必要がある。

- 参考として `Read(...)` 系の deny グロブは**展開される**（`~/.ssh/*` が実在 4 ファイル分の ro マウントに展開されるのを実測）。read と write で挙動が非対称である。
- 保護対象のタスクディレクトリは**継続的に生成・消滅する**ため、静的な設定ファイルでは列挙し続けられない。
- 加えて [§2.2](#22-sandbox-の実装形) のとおり deny 集合は**起動時スナップショット**なので、起動後に作られたタスクは次回起動まで保護されない。

規模自体は障害ではない（現在の `../workers` で必要なのは 39〜51 個の bind であり、実セッションが既に 113 マウントを問題なく扱っている）。**律速は upstream の 1 機能（Linux での `denyWrite` グロブ展開）だけ**である。

→ **V3 は「目標状態」として保持し、次の一歩にはしない。** Claude Code 更新のたびに再確認する。反証条件は明確: 当該バージョンでグロブが展開されるようになれば、この判断は覆る。

### 4.3 hook 層（問い E）

**結論: 既定を反転させる価値はあるが、適用範囲を「sandbox が効かない窓」に絞ること。範囲を絞れば派遣は構造的に止まらない。**

現行の fail-open は「窓口の全 Bash が対象なので締めすぎると業務が止まる」という意図的な妥協である（フック自身のコメントに明記）。その懸念は正しいが、実測すると**コストは想定より小さく、しかも現行方式の偽陽性のほうが大きい**。

反転案（P1: 「再帰削除の動詞を持ち、対象が保護対象外だと静的に証明できないものはブロック」）を実コーパスに適用した結果:

| 指標 | 実測値 |
|---|---|
| 新規にブロックされるコマンド（11,705 件中） | **13** |
| うち現在インストール済みの窓口＋ディスパッチャー範囲 | **1** |
| 形 | すべて `rm -rf $SCRATCH_VAR` 型（変数・コマンド置換由来で対象が解決できない） |

**決定的な性質**: この規則は**削除の動詞にしか発火しない**。したがって `mkdir` / `git worktree add` / ブリーフ書き込みを**構造的にブロックしえない**。

> **ブリーフの制約「偽陽性でワーカー派遣が止まる形は不可」は、この形なら構造的に満たされる。** 派遣の経路には削除動詞が現れないためである。

ただし範囲拡大には注意が要る実測がある。ワーカー自身にまで同じ規則を広げると、**正当なビルド衛生のイディオムが 3 種類巻き込まれる**（`rm -rf dist build *.egg-info` / `rm -rf __pycache__` / フィクスチャ掃除）。これらはワーカー設定が既に export している `$WORKER_DIR` による carve-out で保存できる。

**現行の文字列照合を残したまま反転規則を足す（HYBRID）のは推奨しない。** 現行の照合こそが偽陽性の発生源であり（適合率 5.9%）、それを残すと反転規則の利得を打ち消す。**置き換える**のが正しい。

### 4.4 schema と実配布のずれ（問い C）

**結論: これは「実配布が古い」問題ではない。schema 側の誤導出である。**

#### 4.4.1 事実関係

**実測**:

- 窓口 role の生成先は `.claude/settings.local.json`（schema の `settings_paths` がそう定義している）。**この実ファイルに `sandbox` キーは存在しない**。
- `.claude/settings.json`（リポジトリ共有・git 追跡下）には `sandbox` があるが、こちらは schema の `repo_shared` に対応し、`repo_shared` に `sandbox` の宣言は無い。つまり**どの role 定義にも対応しない手書き**である。
- schema の `roles.secretary.sandbox` には `additionalDirectories: ["{claude_org_path}/../workers"]` がある。

#### 4.4.2 「再生成すると防御が緩む」は成り立たない

当初、「`/org-setup` を流し直すと schema が反映されて `../workers` に書けるようになる（＝防御が緩む）」という懸念があった。**実測の結果、その経路は存在しない。**

```
$ claude-org-runtime settings generate --role secretary --role-kind org ...
error: settings generate does not support --role-kind org
       (org settings.local.json files are hand-maintained; ...)

$ python tools/org_setup_prune.py --role secretary --dry-run
=== secretary: .../.claude/settings.local.json ===
  (no changes)
```

- runtime の generator は **org role を設計上拒否**する（窓口・ディスパッチャー・キュレーターの設定はハンドメンテ）。
- 実際の書き手である [`tools/org_setup_prune.py`](../../tools/org_setup_prune.py) は、**プロジェクト側 role の `sandbox` キーを設計上触らない**（docstring に明記。`--user-common-sandbox` モードだけがユーザーレベル設定に限定マージする）。
- [`tools/check_role_configs.py`](../../tools/check_role_configs.py) には `sandbox` への参照が**1 件も無い**。現状 OK を返す。

→ **`roles.secretary.sandbox` は完全に不活性である。書き手も検証者も存在しない。**

したがって真の欠陥は「再生成で黙って緩む」ではなく、その逆である:

> **宣言された防御方針が、発効する経路を持たないまま放置されており、しかもそれを検出する仕組みが無い。**

#### 4.4.3 揃える方向: schema 側を削除する

[§2.1](#21-いま-workers-を守っているのはフックではない) のとおり `additionalDirectories` は **write の許可**であり、read には不要である。ところが schema の当該エントリは、その根拠として契約書の「**Read** surface (prescriptive)」節を引いている。**読み取り要件を、書き込み＋再帰削除の権限に取り違えた誤導出**である。契約書自身の Gap 記述は `additionalDirectories: [<claude_org_path>]` であり `../workers` を含まない。

→ **`{claude_org_path}/../workers` を `roles.secretary.sandbox.filesystem.additionalDirectories` から削除する。実測コストはゼロ**（read は grant 無しで通るため）。現在は何も消費していないので、この編集は既存端末の挙動を一切変えない。価値は「将来に向けられた銃を外すこと」にある。

## 6. 推奨と段階移行

### 6.1 推奨: O5（多層。ただし重複ではなく分業）

単層に寄せない理由は、各層の**バイパス条件が相補的**だからである:

| 層 | 効かなくなる条件 | 固有の価値 |
|---|---|---|
| L3 sandbox | `dangerouslyDisableSandbox` / bwrap 不在 + `failIfUnavailable:false` | **プログラム内部の削除を含めて意図を見ずに止める唯一の層** |
| L4 hook | シェル文字列の曖昧さ（原理的） | `bypassPermissions` でも `dangerouslyDisableSandbox` でも**発火する唯一の層** |
| L2 permissions | ディスパッチャーの恒久 `bypassPermissions` で無効 | — |

重なりは正確である。**L3 は「sandbox 無効呼び出し」以外のすべてを覆い、L4 の固有価値はまさにその呼び出しにだけある。** 現行設計が失敗しているのは、L4 に L3 の仕事を全コマンド表面で肩代わりさせているからである。

### 6.2 3 つの具体的な動き

1. **L3 — 今の防御を「偶然」から「意図」へ。** schema から `{claude_org_path}/../workers` を削除する（[§4.4.3](#443-揃える方向-schema-側を削除する)）。実測コストゼロ・挙動変化ゼロ。同時に、宣言が不活性であること自体を検出する仕組みを入れる（現状 `check_role_configs.py` は `sandbox` を見ていない）。

2. **L3b — 「任意のシェル文字列に対して sandbox を切る」のをやめ、「監査済みの 1 本のプログラムに対してだけ切る」。** `workers_root` 配下への書き込みが正当に必要な操作は列挙可能で少ない（provisioning = ディレクトリ作成・`git worktree add`・ブリーフ書き込み・clone、および close = `git worktree remove --force`）。これを 1 本のヘルパーに集約し、**そのコード自身が containment を表明する**（対象が `workers_root` 配下に解決されること、`<slug>` か `<slug>/.worktrees/<task>` の形であること、削除は `git worktree list` が worktree と認めたパスに限ること）。これが「シェル文字列からは何が削除されるか決定できない」への正面からの答えである — **文字列に問うのをやめる**。

   **確定した脅威モデルが (c) を含むため、この containment 表明は必須要件である**（[§3.3](#33-確定した脅威モデル)）。同じ pass で [§0.2](#02-フックでは原理的に見えない削除経路がコードとして実在する) の containment 欠如も塞ぐ。対象は「削除を行うプログラム」全般であり、`curator_archive` はその代表例にすぎない。

3. **L4 — フックを固有の守備範囲へ絞る。** 「workers パスの文字列を含み `rm -r` を含む任意の Bash」から、「**再帰削除の動詞を持ち、対象が保護対象外だと静的に証明できないもの**」へ再照準する。相対パスの解決には PreToolUse ペイロードが既に持っている `cwd` を使う。重み付けは `dangerouslyDisableSandbox` を伴う呼び出し（L3 が不在になる唯一の窓）に置く。実測コストは 11,705 件中 13 件、現インストール範囲では 1 件。**削除動詞にしか発火しないので派遣は構造的に止まらない。**

### 6.3 段階移行（既存端末を壊さない順序）

各段階は**単独で安全**であり、前段が未適用の端末でも壊れない。

| 段階 | 内容 | 未再生成の端末への影響 | 検証 |
|---|---|---|---|
| **1** | ガードの版検査を入れる（[§0.1](#01-動いているガードのバージョンを誰も検査していない)）。配備されているフックが期待の版かを起動時に検査し、不一致を可視化する | 影響なし（検査のみ） | 旧版を意図的に置いて検出されることを確認 |
| **2** | schema から `../workers` の write grant を削除。併せて「宣言が不活性であること」の検出を追加 | **影響なし**（誰も消費していない。実測済み） | `check_role_configs` に sandbox 検査が入り、現状を落とさないこと |
| **3** | L3b のヘルパーを**追加**として実装（既存経路は残す） | 影響なし（追加のみ） | 新旧経路の結果が一致すること |
| **4** | 委譲・close をヘルパー経由へ切り替え。`curator_archive` に containment 表明を追加 | ヘルパー未配備の端末は旧経路のまま動く | 派遣・close の実走 |
| **5** | フックを反転規則へ**置換**。まず **shadow モード**（判定を記録するだけでブロックしない）で観測期間を置く | shadow の間は挙動不変 | 実コマンド列で偽陽性ゼロを確認してから有効化 |
| **6** | （前提が整えば）close を移動方式へ、その後 O4 のタスク単位 ro 列挙 | — | Claude Code の `denyWrite` グロブ展開が入ったら再訪 |

**段階 5 の shadow モードは省略しない。** [§1.2](#12-現行フックの改修履歴が示すもの) のとおり、この組織では締める変更が実際に正当な操作を 2 度止めている。

### 6.4 ガードの適用範囲には穴がある（ただし多数派は `../workers` 側）

**実測**（`.state/state.db` の読み取り専用コピーに対して直接集計）:

| 母集団 | `../workers` 配下 | ja リポジトリ内 `.worktrees/` |
|---|---|---|
| 登録済み `worker_dirs` 63 件（全件 `active`） | **54** | 9 |
| 完了した Pattern B の run のうち `worker_dir` が紐付く 33 件 | **26** | 7 |

したがって**ワーカー成果物の多数派は `../workers` 配下にあり、現行ガードの適用範囲はその点では正しい**。

しかし ja リポジトリ内の `.worktrees/` にも実体があり（登録 9 件 / 紐付く close 7 件）、**そこは現行フックの対象外**である（フックは `workers_dir` にのみ反応する）。「マウントが無いこと」による防御も効かない — そこは窓口の cwd 配下であり、書けなければリポジトリ作業そのものができないためである。

→ **保護対象の定義を `workers_dir` から「ワーカー成果物ディレクトリ全体」へ広げる**。ただしこれは「守る対象を取り違えていた」のではなく、**少数だが実在する穴を塞ぐ**位置づけである。

> **計測上の注意**: 完了した Pattern B の run は 137 件あるが、`worker_dir` が紐付いているのは 33 件だけである。上表の close 側の数値は**下限**であり、全体の分布を代表するとは限らない。分布の断定には別途の集計が要る。

## 7. 不変条件（実装時に守るべき契約）

- **INV-1**: 抑止を現状より弱める変更を含めない。段階 2 の schema 編集は、実測で挙動変化ゼロであることを確認したうえで行う。
- **INV-2**: 派遣（`mkdir` / `git worktree add` / ブリーフ書き込み）の経路に、偽陽性で止まりうる判定を置かない。フックの反転規則は**削除動詞にのみ**発火する。
- **INV-3**: 再生成を前提とする変更は、未再生成の端末で壊れない段階順で入れる（[§6.3](#63-段階移行既存端末を壊さない順序)）。
- **INV-4**: 締める変更は shadow モードでの観測を経てから有効化する。
- **INV-5**: ガードは「無効化されたら分かる」こと。黙って `exit 0` に落ちる経路を増やさない。

## 8. 残存リスク・未解決・再訪条件

- **コミット前の作業ファイルは、どの案でも守れない。** ワーカーディレクトリが書ける以上、そこにある未コミットの変更は削除されうる。守れるのは「コミット済みの成果」であり、そこは既存の GitHub remote が担う（実測: 12 プロジェクト中 7 つが ahead=0 で remote に同期済み）。remote 未接続の残渣は特定済みで小さい。
- **`dangerouslyDisableSandbox` の窓は残る。** L4 がそこを守るが、L4 は原理的に不完全である。L3b（特権操作の集約）はこの窓自体を縮小するための施策であり、窓を消すものではない。
- **O4 の再訪条件**: Linux 版 Claude Code で `sandbox.filesystem.denyWrite` のグロブが展開されるようになること。現行 2.1.220 では展開されない（実測）。バージョン更新のたびに確認する。
- **未検証**: 本書の実測はすべて単一環境（WSL2 / ext4 / 単一ユーザー）で行った。他環境、特に非 WSL の Linux や macOS での挙動は確認していない。sandbox の抑制規則が環境依存であることは契約書に既出であり、移植時は再測定が要る。

## 9. 付録: 実測ログ

### 9.1 作成と削除の分離（マウント形ごと）

```
# rw 親 + ro 子
bwrap --bind / / --proc /proc --dev /dev --ro-bind $T/wk/existing $T/wk/existing sh -c '...'
  mkdir $T/wk/newproj              -> OK
  rm -r $T/wk/existing             -> cannot remove '.../deep/file.txt': Read-only file system
  touch $T/wk/existing/probe       -> Read-only file system

# ro 親 + rw 子 + ro .git
bwrap --bind / / --proc /proc --dev /dev \
      --ro-bind $T/wk $T/wk --bind $T/wk/proj-a $T/wk/proj-a \
      --ro-bind $T/wk/proj-a/.git $T/wk/proj-a/.git sh -c '...'
  echo b > $W/proj-a/CLAUDE.local.md   -> OK
  rm -rf $W                            -> cannot remove '.../proj-a/.git/HEAD': Read-only file system
    working file : DESTROYED
    git history  : SURVIVED
```

### 9.2 `additionalDirectories` が write の許可であること

```
ls ../workers/                             -> OK
grep -c "org/workers" /proc/self/mountinfo -> 0
```

読めるのにマウントが存在しない。したがって read に grant は不要であり、`additionalDirectories` は write の許可である。

### 9.3 org role の設定は生成されない

```
$ claude-org-runtime settings generate --role secretary --role-kind org ...
error: settings generate does not support --role-kind org
       (org settings.local.json files are hand-maintained; use `settings show --role-kind org` for inspection).

$ python tools/org_setup_prune.py --role secretary --dry-run
=== secretary: .../.claude/settings.local.json ===
  (no changes)

$ grep -c sandbox tools/check_role_configs.py
0
```

### 9.4 sandbox がマウント点を実体化すること

セッション開始直後の `git status` に現れる未追跡の `.bashrc` / `.gitconfig` / `.idea` / `.claude/agents` は、いずれも 0 バイト `-r--r--r--` で `/proc/self/mountinfo` に bind として現れる。sandbox が deny 対象のマウント点を作るために実体化したものであり、リポジトリの内容ではない。
