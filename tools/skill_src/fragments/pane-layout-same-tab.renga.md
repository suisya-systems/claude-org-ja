- **全ペインを同一タブ内に配置する**: ディスパッチャー・キュレーター・全ワーカーを同一タブ内に split で積む。結論は契約 T-§4.2 の「Retained from ratified §4.2」で retained（[`docs/contracts/backend-interface-contract.md`]({{ROOT}}docs/contracts/backend-interface-contract.md)）。根拠は renga の版数ではなく **capability を確立できたか**で読む（各トークンは独立判定 = 契約 T-§cap の independence rule。org は `server_info` の `effective_capabilities` で確立する）:
  - **`caller_scope` / `caller_scope_close_identity` を確立した経路** — pane 制御の scope は one tab wide のまま、解決タブが **caller のタブ**（フォーカス非依存）になる。**2 つのトークンは個別に判定し、一方から他方を導出しない**: `caller_scope` は Group A（`list_panes` / `focus_pane` / `inspect_pane` / `send_keys` / 各 `spawn_*` の `target`）だけを、`caller_scope_close_identity` は Group B（`close_pane` / `set_pane_identity`）だけをゲートする。**確立できた側**では解決タブが caller の所有タブなので**タブを切り替えても `pane_not_found` は解消しない**（タブ切替を復旧手順にしない）が、**確立できていない側は従来どおりフォーカス依存**のまま — `caller_scope` だけの経路では Group B が**ユーザーが見ているタブ**に解決されうる（契約 T-§4.2「Fail-safe consequence for Group B」。`close_pane` は不可逆）。組み合わせによらず scope は one tab wide なので、`new_tab` で子を別タブに置くと `inspect_pane` / `close_pane` / `list_panes` から観測できなくなる（同一タブ要件の現行根拠）
  - **`cross_tab_peers` を確立した経路** — messaging だけが例外（`list_peers` は全タブ列挙、数値 id 宛 `send_message` はタブ横断、stable name は送信側タブ内でのみ解決）。それでも配置要件は変わらない: 契約 T-§4.2 は「messaging 到達性から pane 制御到達性を推論するな」を **MUST** で禁じている
  - **いずれの capability も確立できない経路**（renga 1.x を含む pre-capability backend） — pane 制御は**フォーカス中**のタブに向くため、フォーカスが別タブにある間は同タブの生存ペインすら addressable でなくなる。これが 2026-04-20 判明の 1.x 系の歴史的根拠（renga 本体側の対応は suisya-systems/renga#71）で、同じ同一タブ要件に帰着する
  - 文面の SoT と誤読時の分岐手順は [`.claude/skills/org-delegate/references/renga-error-codes.md`](renga-error-codes.md) の `pane_not_found` / `split_refused` 行
